# MIGRATION FROM CHEF TO ANSIBLE

## Executive Summary

This repository contains a **Chef Solo**-based infrastructure stack that provisions a multi-service web application environment. The stack is composed of three local cookbooks (`nginx-multisite`, `cache`, `fastapi-tutorial`) and four external Chef Supermarket dependencies (`nginx 12.3.1`, `memcached 6.1.0`, `redisio 7.2.4`, `ssl_certificate 2.1.0`). The environment is currently developed and tested using **Vagrant with libvirt** on a Fedora 42 guest VM, provisioned via `chef-solo` and Berkshelf.

A partial migration has already been completed for a standalone `nginx` Ansible role (located at `123-fc2c2f/modules/nginx/ansible/roles/nginx`), which serves as a reference implementation and can be reused or adapted during the migration of the `nginx-multisite` cookbook.

**Migration Scope**: 3 local cookbooks → 3 Ansible roles + 1 top-level playbook  
**Complexity**: Medium — the cookbooks are well-structured and self-contained, but contain hardcoded credentials, self-signed SSL certificate generation, and a custom Chef resource (`lineinfile`) that must be replaced with native Ansible modules.  
**Estimated Timeline**: 3–5 sprints (6–10 weeks) for a small team, including testing and validation.

## Module Migration Plan

This repository contains **3 local Chef cookbooks** that each require individual migration planning, plus supporting infrastructure files.

### MODULE INVENTORY

- **nginx-multisite**:
  - Description: Nginx reverse proxy and multi-site web server with SSL termination, security hardening, UFW firewall management, fail2ban intrusion prevention, and sysctl kernel hardening. Serves three internal subdomains (`test.cluster.local`, `ci.cluster.local`, `status.cluster.local`), each with self-signed TLS certificates, HTTP→HTTPS redirect, HSTS, and a full suite of security response headers (X-Frame-Options, CSP, X-Content-Type-Options). Includes a custom `lineinfile` Chef resource for in-place file editing.
  - Path: `cookbooks/nginx-multisite`
  - Technology: Chef
  - Key Features:
    - Five recipes: `default` (orchestrator), `nginx` (install + config), `ssl` (self-signed cert generation via openssl), `sites` (per-vhost config + symlinks), `security` (fail2ban, UFW, sysctl, SSH hardening)
    - ERB templates: `nginx.conf.erb`, `site.conf.erb`, `security.conf.erb`, `fail2ban.jail.local.erb`, `sysctl-security.conf.erb`
    - Static HTML files for three sites: `ci/index.html`, `status/index.html`, `test/index.html`
    - Attribute-driven site definitions (document root, SSL toggle) in `attributes/default.rb`
    - Custom LWRP resource `lineinfile` (regex-based in-place line replacement with backup)
    - Depends on external `nginx ~> 12.0` cookbook from Supermarket

- **cache**:
  - Description: Dual caching layer that installs and configures both Memcached and Redis on the same host. Redis is configured with password authentication (`requirepass`) on port 6379. Includes a `ruby_block` workaround to strip incompatible Redis configuration directives (`replica-serve-stale-data`, `replica-read-only`, `repl-ping-replica-period`, `client-output-buffer-limit`, `replica-priority`) that are generated by the `redisio` cookbook but rejected by the installed Redis version.
  - Path: `cookbooks/cache`
  - Technology: Chef
  - Key Features:
    - Delegates to `memcached` (Supermarket `~> 6.0`) and `redisio` (Supermarket `7.2.4`) community cookbooks
    - Redis password set inline in recipe: `requirepass redis_secure_password_123`
    - Post-install config file patching via `ruby_block` (compatibility hack for redisio-generated config)
    - Redis log directory creation (`/var/log/redis`)
    - Calls `redisio::enable` to activate the Redis service

- **fastapi-tutorial**:
  - Description: Full-stack Python FastAPI application deployment that clones a Git repository, creates a Python 3 virtual environment, installs pip dependencies, provisions a PostgreSQL database with a dedicated user, writes a `.env` configuration file, and registers a systemd service unit for the application. The application is exposed on port 8000 via uvicorn.
  - Path: `cookbooks/fastapi-tutorial`
  - Technology: Chef
  - Key Features:
    - System packages: `python3`, `python3-pip`, `python3-venv`, `git`, `postgresql`, `postgresql-contrib`, `libpq-dev`
    - Git clone from `https://github.com/dibanez/fastapi_tutorial.git` (branch: `main`)
    - Python venv at `/opt/fastapi-tutorial/venv`
    - PostgreSQL user `fastapi` and database `fastapi_db` created via inline `psql` shell commands
    - `.env` file written to `/opt/fastapi-tutorial/.env` with `DATABASE_URL` containing plaintext credentials
    - systemd unit file at `/etc/systemd/system/fastapi-tutorial.service` (uvicorn on `0.0.0.0:8000`)
    - Service runs as `root` (security concern)
    - Hardcoded DB password: `fastapi_password`

### Infrastructure Files

- `Berksfile`: Berkshelf dependency manifest. Declares all three local cookbooks by path and pins four external Supermarket cookbooks (`nginx ~> 12.0`, `memcached ~> 6.0`, `redisio ~> 7.2.4`, `ssl_certificate ~> 2.1`). The `ssl_certificate` entry is commented out in `Berksfile` but active in `Policyfile.rb`. **Migration consideration**: Replace with `requirements.yml` for Ansible Galaxy roles.
- `Policyfile.rb`: Chef Policyfile defining the `nginx-multisite-policy` run list (`nginx-multisite::default`, `cache::default`, `fastapi-tutorial::default`). Pins all cookbook versions. **Migration consideration**: Becomes the top-level Ansible playbook with ordered role application.
- `Policyfile.lock.json`: Locked dependency graph with resolved versions and SHA identifiers for all 8 cookbooks (including transitive deps `selinux 6.2.4`, `ssl_certificate 2.1.0`). **Migration consideration**: Reference for exact version pinning when selecting Ansible Galaxy role equivalents.
- `solo.json`: Chef Solo node JSON — defines the run list and all node attribute overrides (site definitions, SSL paths, security flags). **Migration consideration**: Becomes Ansible `group_vars/all.yml` or host-specific `host_vars`.
- `solo.rb`: Chef Solo configuration file — sets `cookbook_path` and `file_cache_path`. **Migration consideration**: No direct Ansible equivalent; superseded by `ansible.cfg` and inventory.
- `Vagrantfile`: Vagrant VM definition using `generic/fedora42` box with libvirt provider (2 vCPU, 2 GB RAM), private network `192.168.121.10`, port forwards 80→8080 and 443→8443. Provisions via `vagrant-provision.sh`. **Migration consideration**: Can be adapted to use the `ansible` Vagrant provisioner instead of `shell`; the VM spec informs the target environment definition.
- `vagrant-provision.sh`: Bootstrap shell script that installs Chef, Berkshelf, vendors cookbooks, and runs `chef-solo`. **Migration consideration**: Replace entirely with `ansible-playbook` invocation; Berkshelf vendoring step is eliminated.
- `project-plan.md`: X2Ansible tool specification document describing the migration toolchain architecture. Not a Chef artifact — no migration action required.
- `123-fc2c2f/generated-project-metadata.json`: Auto-generated metadata identifying the `nginx` Ansible role at `roles/nginx`. Indicates this directory is the output of a prior migration run.
- `123-fc2c2f/modules/nginx/migration-plan-nginx.md`: Detailed per-component migration plan for the standalone `nginx` role (already migrated). Documents modernization mapping, template changes, and pre-flight checks. **Migration consideration**: Use as a template for writing migration plans for the remaining three cookbooks.
- `123-fc2c2f/modules/nginx/ansible/roles/nginx/`: Fully migrated Ansible role for a generic Nginx web server (not multisite-specific). Includes tasks, handlers, templates (`nginx.conf.j2`, `site.j2`, `default.conf.j2`, `default.j2`), defaults, vars, meta with `argument_specs.yml`, EPEL repo file, and a complete Molecule test suite. **Migration consideration**: This role can serve as the base for the `nginx-multisite` Ansible role — extend it with SSL, security headers, fail2ban, and UFW tasks rather than starting from scratch.

## Migration Approach

### Key Dependencies to Address

- **nginx (12.3.1)** — Chef Supermarket community cookbook used as the base Nginx installer by `nginx-multisite`. **Replace with**: The already-migrated Ansible role at `123-fc2c2f/modules/nginx/ansible/roles/nginx` (extend it) or `nginxinc.nginx` from Ansible Galaxy. The existing role already handles RedHat/Debian package installation, site configuration, and service management.
- **memcached (6.1.0)** — Chef Supermarket cookbook wrapping the Memcached daemon. **Replace with**: `ansible.builtin.package` to install `memcached` + `ansible.builtin.service` to enable/start it, or the `geerlingguy.memcached` Ansible Galaxy role.
- **redisio (7.2.4)** — Chef Supermarket cookbook for Redis installation and multi-instance management. Note: the `cache` cookbook applies a post-install config patch to strip directives that `redisio` generates but the target Redis version rejects. **Replace with**: `geerlingguy.redis` Ansible Galaxy role, or direct `ansible.builtin.package` + `ansible.builtin.template` tasks. The config-patching `ruby_block` must be replaced with `ansible.builtin.lineinfile` (with `regexp` and `state: absent`) — a direct native equivalent.
- **ssl_certificate (2.1.0)** — Locked in `Policyfile.lock.json` but commented out in `Berksfile`; SSL cert generation is handled inline in `nginx-multisite::ssl` via raw `openssl` shell commands. **Replace with**: `community.crypto.openssl_privatekey` + `community.crypto.x509_certificate` Ansible modules from the `community.crypto` collection for idempotent self-signed certificate generation.
- **selinux (6.2.4)** — Transitive dependency pulled in by `redisio`. **Replace with**: `ansible.posix.selinux` module (already handled in the existing nginx Ansible role via `python3-selinux` / `libselinux-python` package installation).
- **Custom `lineinfile` LWRP** (`cookbooks/nginx-multisite/resources/lineinfile.rb`) — A hand-rolled Chef resource that performs regex-based line replacement with file backup. **Replace with**: `ansible.builtin.lineinfile` module, which provides identical functionality natively with `regexp`, `line`, `backrefs`, and `backup` parameters.

### Security Considerations

- **Hardcoded Redis password** (`cache/recipes/default.rb`, line: `'requirepass' => 'redis_secure_password_123'`): Plaintext credential embedded directly in recipe source code. **Migration approach**: Move to `ansible-vault`-encrypted variable (`vault_redis_password`) stored in `group_vars/all/vault.yml`. Reference as `{{ vault_redis_password }}` in the Redis configuration template.
- **Hardcoded PostgreSQL credentials** (`fastapi-tutorial/recipes/default.rb`): Both the DB user password (`fastapi_password`) and the full `DATABASE_URL` are hardcoded in the recipe and written to `/opt/fastapi-tutorial/.env` with mode `0644` (world-readable). **Migration approach**: Encrypt with `ansible-vault`; write `.env` with mode `0600`; consider using `ansible.builtin.template` with a vault-sourced variable.
- **Self-signed SSL certificates**: Generated via raw `openssl` shell `execute` blocks with `not_if` guards. Certificates are placed in `/etc/ssl/certs` and `/etc/ssl/private`. **Migration approach**: Replace with `community.crypto.openssl_privatekey` and `community.crypto.x509_certificate` for fully idempotent, Ansible-native certificate management. For production, integrate Let's Encrypt via `community.crypto.acme_certificate`.
- **SSH hardening** (`nginx-multisite/recipes/security.rb`): Disables root login and password authentication via `sed` on `/etc/ssh/sshd_config`, controlled by node attributes `security.ssh.disable_root` and `security.ssh.password_auth`. **Migration approach**: Replace `sed` commands with `ansible.builtin.lineinfile` tasks using `regexp` matching. Expose as boolean role variables with the same defaults.
- **UFW firewall** (`nginx-multisite/recipes/security.rb`): Configured via raw `ufw` shell commands with `not_if` idempotency guards. **Migration approach**: Use `community.general.ufw` module for fully declarative, idempotent firewall rule management.
- **FastAPI service running as root** (`fastapi-tutorial/recipes/default.rb`, `User=root` in systemd unit): A significant privilege escalation risk. **Migration approach**: Create a dedicated `fastapi` system user and group; update the systemd unit template to run as that user. Add `ansible.builtin.user` task to the role.
- **`.env` file permissions** (`fastapi-tutorial/recipes/default.rb`): Written with mode `0644`, exposing `DATABASE_URL` with credentials to all local users. **Migration approach**: Set mode to `0600` and owner to the dedicated `fastapi` service user.
- **Credential count summary**:
  - `cache` cookbook: 1 hardcoded secret (Redis `requirepass`)
  - `fastapi-tutorial` cookbook: 2 hardcoded secrets (PostgreSQL password in `psql` command + `DATABASE_URL` in `.env`)
  - `nginx-multisite` cookbook: 0 runtime secrets (SSL certs are self-signed and generated at provision time)
  - **Total: 3 credentials requiring vault migration**

### Technical Challenges

- **Custom `lineinfile` LWRP replacement**: The `nginx-multisite` cookbook ships its own `lineinfile` resource (`resources/lineinfile.rb`) that replicates Ansible's built-in `lineinfile` module. While the direct replacement is straightforward (`ansible.builtin.lineinfile`), all call sites must be audited to ensure `match` regex patterns are correctly translated to Ansible `regexp` syntax.
- **`ruby_block` config-patching in `cache`**: The Redis post-install config patch (`ruby_block "fix_redis_config"`) uses Ruby string manipulation to strip incompatible directives from `/etc/redis/6379.conf`. This must be translated to multiple `ansible.builtin.lineinfile` tasks with `regexp` and `state: absent`. The underlying version incompatibility between `redisio 7.2.4` and the target Redis package must be investigated — if `geerlingguy.redis` is used instead, this workaround may be unnecessary entirely.
- **Attribute-to-variable mapping for multi-site configuration**: The `nginx-multisite` cookbook uses a nested Chef node attribute hash (`node['nginx']['sites']`) to drive site creation loops in three separate recipes (`nginx.rb`, `ssl.rb`, `sites.rb`). This must be translated to an Ansible list-of-dicts variable structure (similar to `nginx_sites` in the existing Ansible role's `defaults/main.yml`) and the three recipe loops must be consolidated into a single Ansible role with looped tasks.
- **`ssl_certificate` cookbook ambiguity**: The cookbook is commented out in `Berksfile` but present and locked in `Policyfile.lock.json`. SSL cert generation is handled directly in `nginx-multisite::ssl` via `openssl` shell commands. The migration must confirm whether `ssl_certificate` is actually invoked at runtime or is a vestigial lock entry, and remove it from the dependency manifest accordingly.
- **Fedora 42 vs. declared platform support**: The Vagrantfile uses `generic/fedora42`, but all `metadata.rb` files declare support for Ubuntu ≥ 18.04 and CentOS ≥ 7.0 only. The `vagrant-provision.sh` script uses `apt-get`, which will fail on Fedora. This platform inconsistency must be resolved before migration: either align the Vagrant box with the declared target OS, or add Fedora/RHEL support to all roles.
- **`chef-solo` run list ordering**: The policy run list (`nginx-multisite → cache → fastapi-tutorial`) encodes an implicit dependency order. In Ansible, this becomes explicit role ordering in the playbook. The `nginx-multisite` role must complete before `fastapi-tutorial` since the FastAPI app is expected to sit behind the Nginx reverse proxy (port 8000 proxied through Nginx).
- **Git-based application deployment**: `fastapi-tutorial` uses Chef's `git` resource to clone and sync the application repository. The Ansible equivalent (`ansible.builtin.git`) is straightforward, but the `revision: main` tracking means re-runs will always pull the latest commit. A version-pinned deployment strategy (specific tag or SHA) should be considered for production.
- **systemd daemon-reload notification**: The `fastapi-tutorial` recipe uses `notifies :run, 'execute[systemd_reload]', :immediately` to reload systemd after writing the unit file. In Ansible, this is handled by `ansible.builtin.systemd` with `daemon_reload: true` in a handler, which is cleaner and fully idempotent.

### Migration Order

1. **`nginx-multisite`** *(Priority 1 — foundational, no upstream cookbook dependencies within this repo)*  
   Extend the already-migrated `nginx` Ansible role (`123-fc2c2f/modules/nginx/ansible/roles/nginx`) with SSL certificate generation (`community.crypto`), per-site vhost templates, fail2ban configuration, UFW rules (`community.general.ufw`), and sysctl kernel hardening. This role is the entry point for the entire stack and must be stable before the application layer is deployed. The existing Molecule test suite provides a ready scaffold for validation.

2. **`cache`** *(Priority 2 — standalone service, no dependency on nginx or fastapi)*  
   Migrate Memcached and Redis installation to a single Ansible role. Replace the `redisio` cookbook with `geerlingguy.redis` (or direct package + template tasks). Translate the `ruby_block` config-patching hack to `ansible.builtin.lineinfile` tasks with `state: absent`. Move the Redis password to `ansible-vault`. Validate with Molecule.

3. **`fastapi-tutorial`** *(Priority 3 — depends on PostgreSQL being available and Nginx being configured as a reverse proxy)*  
   Migrate the application deployment role last. Create a dedicated `fastapi` system user. Replace the inline `psql` shell commands with `community.postgresql.postgresql_user` and `community.postgresql.postgresql_db` modules. Move all credentials to `ansible-vault`. Fix `.env` file permissions. Update the systemd unit template to run as the non-root `fastapi` user. Add a `daemon_reload` handler.

### Assumptions

1. **Target OS alignment**: The declared target platforms (Ubuntu ≥ 18.04, CentOS ≥ 7) are assumed to be the actual production targets. The Fedora 42 Vagrant box is treated as a development convenience only. The Ansible roles will be written to support Ubuntu 22.04 LTS and RHEL 9 as primary targets, consistent with the existing migrated `nginx` role's platform matrix.
2. **Self-signed certificates are intentional**: The `ssl` recipe generates self-signed certificates with a 365-day validity. This is assumed to be correct for the internal `*.cluster.local` domains. No Let's Encrypt or external CA integration is assumed unless explicitly requested.
3. **Single-host deployment**: All three cookbooks are applied to the same node in the Chef run list. The Ansible migration will produce a single playbook targeting one host group, with all three roles applied in sequence. No multi-host or distributed topology is assumed.
4. **`ssl_certificate` cookbook is unused at runtime**: The cookbook is commented out in `Berksfile` and no recipe explicitly calls `include_recipe 'ssl_certificate'`. It is assumed to be a vestigial lock entry and will not be migrated.
5. **Redis version compatibility**: The `ruby_block` config-patching hack in `cache` suggests the `redisio 7.2.4` cookbook generates configuration directives incompatible with the Redis version available on the target OS. It is assumed that using `geerlingguy.redis` or direct package installation will install a compatible Redis version that does not require post-install patching.
6. **PostgreSQL is installed on the same host as FastAPI**: The `DATABASE_URL` in the `.env` file uses `localhost`. It is assumed PostgreSQL and the FastAPI application co-reside on the same VM.
7. **The existing `nginx` Ansible role is a valid migration reference**: The role at `123-fc2c2f/modules/nginx/ansible/roles/nginx` has passed `ansible-lint` validation (with minor warnings) and Molecule testing. It is treated as a canonical reference for Ansible best practices in this project (FQCN module names, quoted octal modes, `ansible_facts` dictionary access, Python 3 template syntax).
8. **Vagrant/libvirt is the development environment only**: No Ansible inventory for a production environment exists yet. The migration plan assumes a new `inventory/` directory will be created with appropriate `group_vars` and `host_vars` to replace `solo.json`.
9. **`vagrant-provision.sh` will be replaced entirely**: The shell bootstrap script (Chef install, Berkshelf vendor, chef-solo run) has no Ansible equivalent and will be superseded by a `vagrant-provision.sh` that simply calls `ansible-playbook`, or by switching the Vagrantfile to use the native `ansible` provisioner.
10. **No Chef Server or Chef Vault in use**: The stack uses `chef-solo` exclusively. There are no encrypted data bags, Chef Vault items, or Chef Server API calls to migrate. All secrets are currently stored as plaintext in recipe source code and must be migrated to `ansible-vault`.
