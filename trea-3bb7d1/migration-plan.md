# MIGRATION FROM CHEF TO ANSIBLE

## Executive Summary

This repository contains a **Chef Solo**-based infrastructure automation project that provisions a single server
(Fedora/Ubuntu/CentOS) running Nginx with three SSL-enabled virtual hosts, two caching layers (Memcached and Redis),
and a FastAPI Python web application backed by PostgreSQL. The entire stack is driven by a `Policyfile.rb` and
exercised locally via Vagrant (libvirt provider).

| Dimension | Detail |
|---|---|
| Technology | Chef Solo ≥ 16.0 (Berkshelf + Policyfile workflow) |
| Local dev environment | Vagrant + libvirt (`generic/fedora42`, 2 vCPU / 2 GB RAM) |
| Number of local cookbooks | 3 |
| External cookbook dependencies | 5 (nginx 12.3.1, memcached 6.1.0, redisio 7.2.4, ssl\_certificate 2.1.0, selinux 6.2.4) |
| Credential exposure | ⚠️ Multiple plaintext secrets present |
| Estimated migration effort | **2–3 sprints** (4–6 weeks for a small team) |

The migration is **moderate in complexity**. All three cookbooks map cleanly to well-supported Ansible
collections/modules. The primary risk areas are secret management (hardcoded passwords), idempotency gaps introduced
by raw `execute`/`sed` blocks, and the Redis configuration workaround that patches the generated config file in
place.

---

## Module Migration Plan

This repository contains **3 local Chef cookbooks** that require individual migration planning, plus 5 external
Supermarket cookbook dependencies that must be replaced with Ansible equivalents.

### MODULE INVENTORY

**CRITICAL PATH VERIFICATION:**
All paths below were verified directly from the repository tree and file contents.

---

- **nginx-multisite**
  - **Description**: Nginx multi-virtual-host server with SSL termination across three named subdomains
    (`test.cluster.local`, `ci.cluster.local`, `status.cluster.local`). Manages the full Nginx lifecycle:
    package installation, main `nginx.conf` from an ERB template, per-site `sites-available/` configs with
    HTTP→HTTPS redirect, TLSv1.2/1.3-only SSL using self-signed certificates generated by OpenSSL, security
    hardening headers (HSTS, CSP, X-Frame-Options, etc.), and static `index.html` content per site. This is the
    primary cookbook and runs first in the policy run-list.
  - **Path**: `cookbooks/nginx-multisite`
  - **Technology**: Chef
  - **Key Features**:
    - Four sub-recipes: `security`, `nginx`, `ssl`, `sites` (orchestrated by `default.rb`)
    - ERB templates: `nginx.conf.erb`, `site.conf.erb`, `security.conf.erb`, `fail2ban.jail.local.erb`,
      `sysctl-security.conf.erb`
    - Custom LWRP resource `lineinfile` (mirrors Ansible's `lineinfile` module directly)
    - Self-signed certificate generation via `openssl req -x509` per site
    - UFW firewall management (default-deny, allow SSH/80/443)
    - fail2ban installation and configuration
    - SSH hardening: `PermitRootLogin no`, `PasswordAuthentication no` via `sed` on `sshd_config`
    - Kernel security tuning via `/etc/sysctl.d/99-security.conf`
    - Attributes-driven site map (`solo.json` overrides `attributes/default.rb`)

---

- **cache**
  - **Description**: Dual-layer caching cookbook that installs and configures both Memcached (via the community
    `memcached` cookbook) and Redis (via `redisio`). Redis is configured to listen on port 6379 with password
    authentication. A post-configuration `ruby_block` hack patches the generated Redis config file to strip
    deprecated directive lines that cause `redisio` 7.2.4 to fail on newer Redis versions.
  - **Path**: `cookbooks/cache`
  - **Technology**: Chef
  - **Key Features**:
    - Delegates Memcached setup entirely to the external `memcached ~> 6.0` cookbook
    - Delegates Redis setup to `redisio 7.2.4` + `redisio::enable`
    - Hardcoded Redis password: `redis_secure_password_123` (plaintext in `recipes/default.rb`)
    - Post-install `ruby_block` that surgically removes deprecated Redis directives
      (`replica-serve-stale-data`, `replica-read-only`, etc.) — indicates a version mismatch between
      `redisio` and the installed Redis server
    - Creates `/var/log/redis` directory with correct ownership

---

- **fastapi-tutorial**
  - **Description**: Full-stack Python application cookbook that provisions a FastAPI web service with a
    PostgreSQL backend. Clones the application from a public GitHub repository, creates a Python virtual
    environment, installs pip dependencies, writes a `.env` file with database credentials, and installs a
    systemd unit file to manage the service. PostgreSQL is installed from the OS package manager and the
    application database/user is created via inline `psql` commands.
  - **Path**: `cookbooks/fastapi-tutorial`
  - **Technology**: Chef
  - **Key Features**:
    - System packages: `python3`, `python3-pip`, `python3-venv`, `git`, `postgresql`, `postgresql-contrib`,
      `libpq-dev`
    - Git clone from `https://github.com/dibanez/fastapi_tutorial.git` (branch `main`) to
      `/opt/fastapi-tutorial`
    - Python venv at `/opt/fastapi-tutorial/venv`; dependencies from `requirements.txt`
    - Hardcoded PostgreSQL credentials: user `fastapi` / password `fastapi_password` (plaintext in both
      `recipes/default.rb` and the generated `.env` file at `/opt/fastapi-tutorial/.env`)
    - `DATABASE_URL` written in cleartext to `/opt/fastapi-tutorial/.env` (mode `0644` — world-readable ⚠️)
    - systemd service (`fastapi-tutorial.service`) running uvicorn on `0.0.0.0:8000` as `root` ⚠️
    - Database/user creation uses `|| true` guard to achieve idempotency; not fully idempotent on
      credential rotation

### Infrastructure Files

- **`Policyfile.rb`**: Chef Policyfile defining the run-list (`nginx-multisite::default`, `cache::default`,
  `fastapi-tutorial::default`) and all cookbook version constraints. The canonical source of truth for
  dependency versions. Must be replaced by an Ansible playbook with explicit role ordering.

- **`Policyfile.lock.json`**: Locked dependency graph. Records exact resolved versions for all 8 cookbooks
  (3 local + 5 community). Use this to verify target Ansible collection/module versions during migration.
  Notably locks `ssl_certificate 2.1.0` and `selinux 6.2.4` even though neither is explicitly declared as a
  direct dependency in local cookbook `metadata.rb` files (they are transitive via `redisio`).

- **`Berksfile`**: Berkshelf dependency file (superseded by Policyfile in practice). Notes that
  `ssl_certificate` is commented out at the Berkshelf level but is present and locked in the Policyfile —
  indicates a discrepancy between the two resolver files.

- **`solo.rb`**: Chef Solo configuration. Defines `file_cache_path` and `cookbook_path`. Maps directly to
  Ansible's inventory/playbook working directory. No secrets.

- **`solo.json`**: Chef Solo node JSON — provides node attribute overrides for site definitions, SSL paths,
  and all security flags. This is effectively the Ansible host/group `vars` file and must be fully translated
  into Ansible variables or inventory vars.

- **`Vagrantfile`**: Vagrant environment definition using the `libvirt` provider, `generic/fedora42` box,
  private network IP `192.168.121.10`, and port forwards 8080→80 / 8443→443. Provisions via
  `vagrant-provision.sh`. Maps to an Ansible development inventory targeting a local VM.

- **`vagrant-provision.sh`**: Bootstrap shell script that installs Chef, Berkshelf, vendors cookbooks, and
  runs `chef-solo`. This becomes obsolete in its entirety after migration; replace with `ansible-playbook`
  invocation (potentially kept as a thin wrapper for Vagrant compatibility).

- **`cookbooks/nginx-multisite/resources/lineinfile.rb`**: Custom Chef LWRP that replicates Ansible's
  built-in `ansible.builtin.lineinfile` module. Can be deleted after migration since the native Ansible
  module covers the same functionality.

### Target Details

- **Operating System**: Declared support for Ubuntu ≥ 18.04 and CentOS ≥ 7.0 in all cookbook `metadata.rb`
  files. The Vagrant box is `generic/fedora42`. The provisioning script uses `apt-get`, indicating the
  primary tested target is **Debian/Ubuntu**. Nginx templates use Debian path conventions
  (`/etc/nginx/sites-available`, `/etc/nginx/sites-enabled`, `www-data` user). Recommend targeting
  **Ubuntu 22.04 LTS** or **Ubuntu 24.04 LTS** as the primary Ansible target; add RHEL/CentOS 9 support as
  a secondary target if required.
- **Virtual Machine Technology**: **libvirt/KVM** (explicit `config.vm.provider "libvirt"` in `Vagrantfile`).
- **Cloud Platform**: Not specified. No cloud-specific tooling, metadata endpoints, or cloud-init
  configuration is present in the repository.

## Migration Approach

### Key Dependencies to Address

| Chef Dependency | Locked Version | Ansible Replacement |
|---|---|---|
| `nginx` (community cookbook) | 12.3.1 | `ansible.builtin.package` + `ansible.builtin.template` or `nginxinc.nginx` collection |
| `memcached` (community cookbook) | 6.1.0 | `ansible.builtin.package` + `ansible.builtin.service` (Memcached has no dedicated collection; straightforward package install) |
| `redisio` (community cookbook) | 7.2.4 | `community.general` or direct `ansible.builtin.package` + `ansible.builtin.template` for `redis.conf`; eliminates the config-patch hack entirely |
| `ssl_certificate` (community cookbook) | 2.1.0 | `community.crypto.x509_certificate` + `community.crypto.openssl_privatekey` (Ansible Collections) |
| `selinux` (transitive via redisio) | 6.2.4 | `ansible.posix.selinux` module (only relevant for RHEL/CentOS targets) |

---

### Security Considerations

- **Hardcoded Redis password** (`redis_secure_password_123` in `cookbooks/cache/recipes/default.rb`):
  Must be migrated to **Ansible Vault** (`ansible-vault encrypt_string`). Create a vaulted variable
  `vault_redis_password` and reference it in the Redis configuration template.

- **Hardcoded PostgreSQL credentials** (`fastapi` / `fastapi_password` in
  `cookbooks/fastapi-tutorial/recipes/default.rb` and written to `/opt/fastapi-tutorial/.env`):
  Must be migrated to Ansible Vault. The `.env` file template must use a vaulted variable and its file
  permissions must be tightened from `0644` to `0600` (currently world-readable on the target host).

- **Self-signed TLS certificates**: The `ssl` recipe generates self-signed certificates using
  `openssl req -x509` with a hardcoded 1-year expiry and static `subj` fields. For production migration,
  replace with `community.crypto` collection tasks (or a Let's Encrypt/ACME workflow via
  `community.crypto.acme_certificate`). For development parity, the `community.crypto.x509_certificate`
  module with `provider: selfsigned` is a direct equivalent.

- **SSH hardening via `sed`**: The `security` recipe patches `sshd_config` by running `sed -i` directly.
  Replace with `ansible.builtin.lineinfile` tasks (which are idempotent by design) or the
  `devsec.hardening.ssh_hardening` role for a more comprehensive posture.

- **FastAPI service runs as `root`**: The systemd unit file sets `User=root`. This is a security risk and
  should be corrected during migration by creating a dedicated system user (e.g., `fastapi`) and updating
  directory ownership accordingly.

- **UFW managed via raw shell commands**: `execute 'ufw_allow_ssh'` etc. use brittle `not_if` guards
  checking `ufw status` output. Replace with `community.general.ufw` module tasks, which are idempotent
  and declarative.

- **No secrets management system in use**: There are no Chef encrypted data bags, Chef Vault references,
  or environment variable injection mechanisms. All secrets are literal strings in recipe files. This
  represents the most significant security debt to resolve before the Ansible migration goes to production.

---

### Technical Challenges

- **Redis config post-patching hack**: `cache::default` includes a `ruby_block` that removes deprecated
  directives from the `redisio`-generated config file after the fact. This signals a version incompatibility
  between `redisio 7.2.4` and the Redis server package available on the target OS. In Ansible, write the
  Redis config directly from a managed template (`ansible.builtin.template`), eliminating the need for any
  patching entirely.

- **Attribute-driven site configuration**: The `nginx-multisite` cookbook iterates over a node attribute
  hash (`node['nginx']['sites']`) to generate per-site directories, files, certificates, and vhost configs.
  This dynamic behaviour must be replicated in Ansible using a `vars` dict and `loop` / `with_items`
  constructs. The site map currently lives in both `attributes/default.rb` and `solo.json` (the latter
  overriding the former); in Ansible, consolidate into a single `group_vars` or `host_vars` YAML file.

- **Berksfile / Policyfile discrepancy**: `ssl_certificate` is commented out in `Berksfile` but is present
  and locked in `Policyfile.lock.json` as a transitive dependency of `redisio`. Since Ansible does not use
  `redisio`, this transitive dependency disappears automatically; however, SSL certificate generation must
  be explicitly handled via `community.crypto` tasks.

- **Custom `lineinfile` LWRP**: `cookbooks/nginx-multisite/resources/lineinfile.rb` reimplements
  line-in-file functionality. No migration work is needed beyond deleting this file — Ansible's
  `ansible.builtin.lineinfile` is a first-class built-in.

- **Idempotency of database provisioning**: The `fastapi-tutorial` recipe uses `|| true` to swallow
  errors from `CREATE USER` / `CREATE DATABASE` psql commands. Replace with the
  `community.postgresql.postgresql_user` and `community.postgresql.postgresql_db` modules, which are
  natively idempotent and handle the "already exists" case cleanly.

- **Git-based application deployment**: The recipe clones `https://github.com/dibanez/fastapi_tutorial.git`
  at `main` and re-runs `pip install` on every Chef run with no version pinning. In Ansible, use
  `ansible.builtin.git` with an explicit `version` (commit SHA or tag) and a `pip` task with
  `state: present`; consider adding a `requirements.txt` hash check for reproducibility.

- **Cross-platform divergence**: Cookbooks declare support for both Ubuntu and CentOS, but all tested paths
  use `apt-get` and Debian-style Nginx layout. If RHEL/CentOS support is required in Ansible, SELinux
  contexts, `firewalld` (instead of UFW), `dnf` package names, and service names (e.g., `nginx` vs
  `httpd`) must all be handled via `when: ansible_os_family == 'RedHat'` conditionals or separate var
  files.

- **Vagrant development environment continuity**: The existing `vagrant-provision.sh` calls Chef directly.
  After migration, replace with an Ansible-compatible provisioner block in `Vagrantfile`
  (`config.vm.provision "ansible_local"` or `"ansible"`) pointing at the new playbook.

### Migration Order

The recommended order minimises dependency risk and allows incremental testing at each stage:

1. **`nginx-multisite` → Ansible role `nginx_multisite`** *(Highest value, self-contained, no external
   service dependencies)*
   - Translate all 4 sub-recipes into task files (`security.yml`, `nginx.yml`, `ssl.yml`, `sites.yml`)
   - Convert ERB templates to Jinja2 (straightforward 1:1 mapping)
   - Replace custom `lineinfile` LWRP with `ansible.builtin.lineinfile`
   - Replace `execute ufw_*` with `community.general.ufw` tasks
   - Replace `sed` SSH hardening with `ansible.builtin.lineinfile`
   - Move `solo.json` site map to `group_vars/all/nginx_sites.yml`

2. **`cache` → Ansible role `cache`** *(Moderate complexity; Redis credential and config-patch issues must
   be resolved)*
   - Add `community.postgresql` collection to `requirements.yml` (for later use)
   - Install Memcached via `ansible.builtin.package` + `ansible.builtin.service`
   - Write Redis config directly from a Jinja2 template using `ansible.builtin.template`; eliminates the
     post-patch hack
   - Store Redis password in Ansible Vault

3. **`fastapi-tutorial` → Ansible role `fastapi_app`** *(Most complex; PostgreSQL, Python venv, systemd,
   secrets, and git deployment all in scope)*
   - Create a dedicated `fastapi` system user; remove `User=root` from the service unit
   - Use `community.postgresql.postgresql_user` and `community.postgresql.postgresql_db`
   - Store DB password in Ansible Vault; set `.env` file mode to `0600`
   - Use `ansible.builtin.git` with pinned revision
   - Use `ansible.builtin.pip` inside the venv
   - Use `ansible.builtin.template` for the systemd unit and `.env` file
   - Use `ansible.builtin.systemd` to manage the service

4. **Vagrant / local dev environment update** *(Finalisation step)*
   - Replace `vagrant-provision.sh` Chef bootstrap with an `ansible_local` Vagrant provisioner
   - Validate the full playbook run against `generic/fedora42` (or switch to `generic/ubuntu2204`)

### Assumptions

1. **Single-server target**: The entire run-list applies to one host. The Ansible migration will produce a
   single playbook with three roles applied sequentially. If multi-host topology is introduced later,
   inventory groups and role decomposition will need to be revisited.

2. **Ubuntu is the primary target OS**: Despite dual support claims in `metadata.rb`, all code paths use
   `apt-get`, Debian Nginx conventions, and UFW. The migration plan targets Ubuntu. RHEL/CentOS support is
   treated as out-of-scope unless explicitly required.

3. **Self-signed certificates are acceptable for development**: The `ssl` recipe generates self-signed
   certificates. The Ansible migration will replicate this behaviour using `community.crypto` for
   development. A decision on production certificate strategy (Let's Encrypt, internal CA, etc.) is
   outstanding and must be made before the production rollout.

4. **External community cookbooks have no custom patches**: `nginx 12.3.1`, `memcached 6.1.0`,
   `redisio 7.2.4`, and `ssl_certificate 2.1.0` are assumed to be used as-is from Chef Supermarket. No
   local overrides to these cookbooks were found in the repository tree.

5. **The `ssl_certificate` community cookbook is unused at runtime**: It appears in `Policyfile.lock.json`
   as a transitive dependency of `redisio` but is commented out in `Berksfile` and not referenced in any
   local recipe. It will not require a direct Ansible equivalent.

6. **Ansible Vault will be the secrets backend**: No external secrets manager (HashiCorp Vault, AWS
   Secrets Manager, etc.) is currently in use. The migration plan assumes Ansible Vault is sufficient. If
   the team moves to an external secrets manager, the vaulted variable references can be swapped out
   without changing role logic.

7. **The FastAPI GitHub repository is accessible and stable**: The `fastapi-tutorial` recipe clones a
   public repository at the `main` branch with no pinned revision. The migration plan assumes this
   repository will remain accessible and that a stable commit SHA or tag will be identified and pinned
   during migration.

8. **`project-plan.md` contains non-infrastructure content**: This file is present in the repository root
   but was not opened as it is not relevant to identifying cookbooks, dependencies, or infrastructure
   configuration. If it contains design decisions that affect the migration, it should be reviewed
   separately by the migration team.

9. **Vagrant remains the local development environment**: The migration preserves Vagrant as the local
   testing platform, switching only the provisioner from Chef Solo to Ansible. No containerisation
   (Docker/Podman) or cloud-based dev environment is assumed.

10. **No CI/CD pipeline integration is currently in place**: No `.github/`, `.gitlab-ci.yml`,
    `Jenkinsfile`, or similar pipeline configuration was found in the repository tree. CI/CD integration
    for the new Ansible playbooks is out of scope for this migration plan but should be addressed
    post-migration.
